1. PROJECT OVERVIEW & EXECUTIVE SUMMARY
================================================================================

Project Name: CompassIQ — AI-Powered Ticket Management System

Core Objective: 
Automating customer support ticket triage, classification, priority prediction, 
department routing, and historical resolution retrieval using NLP and Machine 
Learning for consumer electronics customer support.

Problem Statement & Motivation:
Manual ticket routing delays response times and causes misrouting. CompassIQ 
automates categorization, surfaces Top-3 historical ticket solutions, and 
optimizes support staff workflows through intelligent AI-driven routing and 
recommendation systems.

Key Innovation:
- Real-time NLP-based ticket classification using TF-IDF and Logistic Regression
- Top-3 historical similar ticket retrieval using cosine similarity
- Dynamic department routing based on predicted categories
- Role-based access control with security gatekeeping
- Interactive analytics and fraud detection capabilities

================================================================================
2. SYSTEM ARCHITECTURE & COMPLETE WORKFLOW
================================================================================

End-to-End Workflow:

1. Registration & Security Gatekeeping
   - Customer signs up with Bill No/Product ID for verification
   - Account enters PENDING state awaiting Admin approval
   - Login restricted to APPROVED accounts only

2. Ticket Submission
   - Customer submits complaint with Subject and Description
   - System generates unique Ticket ID (TKT-XXXXXX format)

3. AI Preprocessing & Inference
   - NLP pipeline cleans text (lowercase, punctuation removal, lemmatization)
   - TF-IDF vectorization extracts features from processed text
   - Balanced Logistic Regression predicts Issue Category (5 classes)
   - Priority prediction using balanced ML model (4 levels)
   - Fraud detection via keyword matching + ML classification

4. Top-3 Historical Match Retrieval
   - Cosine similarity identifies nearest historical resolutions
   - Returns top 3 matches with percentage similarity scores
   - Includes historical resolution time estimates

5. Dynamic Ticket Routing
   - Routes to appropriate department: Technical, Billing, Account, General Inquiry
   - Fraud cases automatically routed to Admin_Fraud queue
   - Department agents see only relevant tickets

6. Agent Workspace & Resolution
   - Agent inspects AI recommendations and similar historical tickets
   - Can reference historical solutions in responses
   - Replies to customer and updates ticket status
   - Tracks resolution time and quality

7. Customer Resolution & Feedback
   - Customer views real-time communication thread
   - Visual 5-stage progress tracker shows ticket status
   - Upon resolution, customer submits 1-5 star CSAT rating
   - Optional qualitative feedback collection

8. Admin Intelligence
   - Real-time telemetry dashboard with KPI metrics
   - User approval queue for new registrations
   - Fraud escalation desk for security incidents
   - Interactive Chart.js analytics for department performance

2. TF-IDF feature extraction
3. Category prediction (5 classes: Technical, Billing, Account, General Inquiry, Fraud)

- predicted_category: String classification

- low_confidence: Boolean flag for manual review (< 45% confidence)
- fraud_flagged: Boolean indicating security concern
- similar_matches: List of top 3 historical matches with similarity scores

Enhanced Features:
- Prediction confidence scoring using predict_proba()
- Low confidence flag for human intervention
- Hybrid fraud arbitration (rule-based + ML)

7.1. DATA DISTRIBUTION & IMBALANCE MITIGATION
================================================================================

Baseline Class Distributions:
The training dataset exhibits significant class imbalance, which is typical 
for real-world customer support scenarios:

Issue_Category Distribution:
- Technical: 29.6% (Majority class)
- Billing: 25.2% (Majority class)
- Account: 20.4% (Moderate class)
- General Inquiry: 19.6% (Moderate class)
- Fraud: 5.2% (Minority class - critical for security)

Priority_Level Distribution:
- Low: 38.6% (Majority class)
- Medium: 37.8% (Majority class)
- High: 17.1% (Minority class)
- Critical: 6.5% (Minority class - critical for SLA compliance)

Dual-Layer Imbalance Mitigation Strategy:

1. Feature Space Balancing (SMOTE):
   - Synthetic Minority Oversampling Technique applied to training TF-IDF matrix
   - Generates synthetic samples for minority classes in feature vector space
   - sampling_strategy='auto' automatically balances all classes
   - random_state=42 ensures reproducible results
   - Applied strictly to training partition to prevent data leakage

2. Algorithm-Level Balancing (class_weight='balanced'):
   - Logistic Regression with class_weight='balanced' parameter
   - Automatically adjusts class weights inversely proportional to class frequencies
   - Ensures minority classes contribute appropriately to loss function
   - multinomial Logistic Regression for multi-class classification

Evaluation Metrics for Minority Classes:

Macro F1-Score vs Weighted F1-Score:
- Macro F1: Arithmetic mean of per-class F1-scores (treats all classes equally)
- Weighted F1: Weighted average based on class support (accounts for distribution)
- Macro F1 is preferred for imbalanced datasets as it highlights minority class performance
- Weighted F1 provides overall system performance perspective

Minority Class Performance Monitoring:
- Explicit tracking of Fraud class precision/recall (critical for security)
- Explicit tracking of Critical priority class metrics (critical for SLA)
- Per-class classification reporting during training
- Threshold-based low confidence flagging for manual review

Imbalance Handling Justification:
- SMOTE addresses feature space imbalance without duplicating samples
- class_weight='balanced' ensures fair decision boundaries
- Dual approach provides robust handling of both majority and minority classes
- Macro F1-score serves as primary evaluation metric for fairness assessment

7.2. MODEL SELECTION & LATENCY JUSTIFICATION
================================================================================

Logistic Regression Selection Rationale:

Technical Justification over Deep Learning/LLMs:

1. Deterministic CPU Inference Latency:
   - Average inference time: 10-15 milliseconds per ticket
   - Consistent performance without GPU requirements
   - Predictable latency suitable for real-time classification
   - No cold-start delays or API rate limiting concerns

2. Cost Efficiency:
   - Zero external API costs (no cloud LLM subscriptions)
   - No cloud dependency or network latency
   - Low RAM footprint (~50MB for all models + corpus)
   - Scalable horizontally without incremental cloud costs

3. Operational Simplicity:
   - Self-contained deployment (no external service dependencies)
   - Version control-friendly (serialized artifacts in git)
   - Easy rollback and model versioning
   - No API key management or service authentication

4. Feature Interpretability:
   - Log-odds coefficients provide feature importance analysis
   - Compliance auditing and explainability requirements
   - Debugging capability through coefficient inspection
   - Transparent decision boundaries for regulatory compliance

5. Domain Suitability:
   - TF-IDF + Logistic Regression well-suited for text classification
   - Effective for customer support domain with structured categories
   - Sufficient performance for operational requirements
   - Maintains high accuracy while being computationally efficient

Performance Characteristics:
- Training time: < 5 minutes on 10k samples
- Inference time: 10-15ms per ticket (CPU)
- Memory footprint: ~50MB total (models + corpus)
- Accuracy: 85-92% F1-score on test set
- Scalability: Linear with corpus size

Alternative Approaches Considered:
- Deep Learning (BERT, RoBERTa): Higher accuracy but 100-500ms latency, GPU requirement
- LLM APIs (GPT, Claude): Superior understanding but API costs, rate limits, privacy concerns
- Random Forest: Similar accuracy but higher inference latency (~25ms)
- SVM: Good performance but slower training and prediction

Logistic Regression was selected as the optimal balance of accuracy, latency, cost, and operational complexity for the customer support domain.

7.3. OOV HANDLING & MULTI-MODEL DECOUPLING
================================================================================

Out-of-Vocabulary (OOV) Handling Strategy:

Word N-Gram Fallback:
- TF-IDF vectorizer uses ngram_range=(1, 2) for unigrams and bigrams
- Unigrams capture individual word features even with unknown vocabulary
- Bigrams capture word context and phrase patterns
- Stopword removal preserves meaningful technical terms
- Lemmatization reduces word forms to base forms for better matching

Zero-Vector Mitigation:
- If input text contains no recognized features after preprocessing
- System defaults to "General Inquiry" category with "Low" priority
- Low confidence flag is triggered (confidence < 45%)
- Triggers manual human review for edge cases
- Prevents classification failures on completely novel inputs

Technical Terms Handling:
- Technical support domain includes specific terminology (API, 502, kernel panic)
- These terms are preserved during preprocessing (not in stopword list)
- TF-IDF vectorizer learns domain-specific vocabulary during training
- Lemmatization standardizes word forms while preserving technical meaning
- N-gram combinations capture technical phrases and error codes

Independent Decoupled Classifiers:

Architecture Justification:
- Two separate Logistic Regression models: one for Category, one for Priority
- Independent training prevents category-priority bias leakage
- Allows different class distributions and imbalance handling strategies
- Enables independent model updates and retraining
- Provides flexibility for domain-specific tuning

Advantages Over Chained Pipeline:
- No dependency between category and priority predictions
- Category errors don't cascade to priority classification
- Each model optimized for its specific classification task
- Independent confidence scoring for both predictions
- Easier debugging and performance analysis

Training Independence:
- Category model trained on Issue_Category labels
- Priority model trained on Priority_Level labels
- Separate SMOTE balancing for each target variable
- Independent hyperparameter tuning per model
- Separate evaluation metrics and monitoring

Similarity Metric Normalization:

Cosine Score Scaling:
- Raw cosine similarity scores range from -1.0 to 1.0
- For TF-IDF vectors (non-negative), range is 0.0 to 1.0
- Scores scaled by factor of 100 for human-readable percentage display
- Formula: similarity_percentage = cosine_score × 100
- Example: 0.89 cosine similarity → 89% similarity display

Agent Interface Considerations:
- Percentage format intuitive for support agents
- Consistent with business intelligence dashboards
- Easy threshold setting (e.g., "show matches > 75% similarity")
- Facilitates quick decision-making for historical solution relevance
- Reduces cognitive load compared to raw cosine scores

Implementation Details:
- Scaling performed in ai_engine.py during similarity retrieval
- Consistent across all historical match displays
- Maintains precision to 2 decimal places (e.g., 87.34%)
- Enables similarity-based filtering and sorting in UI
- Supports confidence-based solution recommendation ranking

7.4. COMPUTATIONAL COMPLEXITY & BIG-O ANALYSIS
================================================================================

Algorithm Complexity Analysis:

1. Text Preprocessing (clean_text):
   Complexity: O(L) where L is the token length
   - Lowercase conversion: O(L)
   - Regex pattern matching: O(L)
   - Tokenization: O(L)
   - Stopword removal: O(L) using hash set lookup
   - Lemmatization: O(L) with WordNet dictionary lookups
   Total: O(L) - Linear with text length

2. TF-IDF Vectorization:
   Training Complexity: O(N × V) where N is document count, V is vocabulary size
   - Token counting: O(N × L_avg)
   - Document frequency calculation: O(N × V)
   - IDF computation: O(V)
   - TF-IDF matrix construction: O(N × V)
   
   Inference Complexity: O(V) where V is vocabulary size
   - Token transformation: O(L)
   - Feature extraction: O(V) for sparse matrix multiplication
   - Sparse matrix operations: O(K) where K is non-zero features per document

3. Logistic Regression Inference:
   Complexity: O(C × K) where C is class count, K is non-zero features
   - Decision function computation: O(C × K)
   - Softmax probability calculation: O(C)
   - Predict_proba overhead: O(C × K)
   Total: O(C × K) - Linear with features and classes

4. Sparse Cosine Similarity Retrieval:
   Complexity: O(N × K) where N is historical corpus size, K is non-zero features
   - Sparse matrix dot product: O(N × K) using linear_kernel
   - Similarity score computation: O(N)
   - Top-K selection: O(N log K) using argsort
   - For K=3: O(N) with efficient partial sorting
   Optimized: < 2ms for N=10k historical tickets

Overall System Latency Breakdown:
- Text preprocessing: 2-3ms
- TF-IDF transformation: 3-5ms
- Category prediction: 2-3ms
- Priority prediction: 2-3ms
- Similarity retrieval: 1-2ms
- Total: 10-16ms per ticket (CPU-bound)

Memory Complexity:
- TF-IDF vectorizer: O(V) - Vocabulary storage
- Logistic Regression models: O(C × K) - Coefficient matrices
- Historical corpus: O(N × K_avg) - Sparse matrix storage
- Total memory: ~50MB for typical deployment

Scalability Considerations:
- Linear scaling with corpus size for similarity retrieval
- Constant time for individual predictions
- Batch processing capability for bulk operations
- Horizontal scaling through model sharding if needed

Big-O Summary:
- Preprocessing: O(L)
- Vectorization: O(V) inference, O(N × V) training
- Classification: O(C × K)
- Similarity Search: O(N × K)
- Overall: O(L + V + C × K + N × K) ≈ O(N × K) dominated by similarity search

Scalability Enhancements:

1. Dense Semantic Embeddings Upgrade:
   Current: Sparse TF-IDF vectors (5000 dimensions)
   Proposed: Sentence transformers (all-MiniLM-L6-v2, 384 dimensions)
   
   Benefits:
   - Better semantic understanding beyond keyword matching
   - Cross-lingual capabilities for international support
   - Improved handling of synonyms and context
   - Reduced dimensionality with better representation
   
   Implementation:
   - Replace TF-IDF with sentence transformer embeddings
   - Use FAISS (Facebook AI Similarity Search) for vector indexing
   - Approximate nearest neighbor search for sub-millisecond retrieval
   - GPU acceleration for embedding generation if needed
   
   Trade-offs:
   - Increased model size (~100MB vs ~5MB)
   - Higher inference latency (~50ms vs ~10ms)
   - Requires GPU for optimal performance
   - More complex deployment infrastructure

2. Human-in-the-Loop Active Learning:
   Current: Static model retraining with periodic updates
   Proposed: Continuous learning from agent feedback
   
   Architecture:
   - Feedback collection from agent corrections and overrides
   - Confidence threshold-based sample selection for retraining
   - Automated model versioning and A/B testing
   - Gradual rollout with performance monitoring
   
   Benefits:
   - Models adapt to evolving customer issues and terminology
   - Improved accuracy for domain-specific cases
   - Reduced manual maintenance overhead
   - Self-improving system over time
   
   Implementation:
   - Feedback loop logging (predicted vs actual categories)
   - Uncertainty sampling for high-value training data
   - Scheduled retraining pipelines with validation
   - Model performance drift monitoring

3. Multi-Modal Architecture:
   Current: Text-only processing
   Proposed: Multi-modal ticket analysis
   
   Additional Data Sources:
   - Screenshots and error logs (image processing)
   - System diagnostics and logs (structured data)
   - Customer interaction history (sequential data)
   - Product information and specifications (knowledge graph)
   
   Architecture:
   - Separate encoders for each modality
   - Fusion layer for combined predictions
   - Attention mechanisms for feature importance
   - Cross-modal learning for improved accuracy

4. Distributed Microservices Architecture:
   Current: Monolithic Flask application
   Proposed: Microservices with containerization
   
   Service Decomposition:
   - API Gateway: Request routing and authentication
   - Classification Service: ML model inference
   - Similarity Service: Historical ticket retrieval
   - Notification Service: Email and alert management
   - Analytics Service: Reporting and metrics
   
   Benefits:
   - Independent scaling of different components
   - Technology flexibility per service
   - Improved fault isolation and resilience
   - Easier deployment and updates
   
   Implementation:
   - Docker containerization for each service
   - Kubernetes orchestration for deployment
   - Service mesh for inter-service communication
   - Centralized logging and monitoring

5. Real-Time Streaming Architecture:
   Current: Batch processing per ticket
   Proposed: Real-time event streaming
   
   Architecture:
   - Apache Kafka for event streaming
   - Stream processing for real-time classification
   - Caching layer for frequently accessed data
   - WebSocket for live updates to clients
   
   Benefits:
   - Sub-second classification for urgent tickets
   - Real-time dashboard updates
   - Better handling of ticket spikes
   - Improved customer experience
